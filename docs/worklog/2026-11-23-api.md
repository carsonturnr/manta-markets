# API (build order step 13)

## What
- `/api/v1/fair-values`, `/distributions`, `/cost`, `/pairs`, `/liquidity`: read-only JSON of Manta's own analytics; no order-book levels, trades or bid/ask quotes (lib/api.ts drops them, tested).
- Keys made on /account (max 3, shown once, SHA-256 stored), sent as `Authorization: Bearer manta_…`.
- Limits: 60 units a minute per user (`/cost` 5 units) and a shared cap of 2 uncached venue book reads a second across all API callers (503 + Retry-After when full).
- Migration (applied 2026-11-23): `manta.api_keys` (RLS like the watchlist), `api_usage`, `api_fetches`, `api_venue_budget`, and `manta.api_use()` (security definer, manta_account only).
- `/docs/api` page, linked from /account and the footer.

## Why
Step 13 of docs/product.md: an API of derived analytics, which the venues' data terms allow (decisions 2026-11-17).

## Decisions
- Key check and both limits in one Postgres function: one round trip, and no login can read hashes or counters; `manta_site` stays read-only.
- Per-user, not per-key, limit (3 keys must not triple it). Shared venue cap at a tenth of the measured clean Kalshi rate (~20 books/s; ~40/s drew 429s).
- `/cost` returns `best_price` + `book_time`, never the levels; fee and totals null when the fee rate is unknown.
- Reuses the site's cached reads ("use cache"), so the API adds no load beyond them.

## Verified
`npm test` (39 pass), tsc, lint, `next build`. Against `next start` on the live database with a demo key: 401 (none/unknown key), 200 on all five, 400/404 on a bad /cost, 6 new contracts at once → 2 × 200 + 4 × 503, burst → 429 with Retry-After. Kalshi fee checked by hand: 0.07·500·0.47·0.53 = 8.7185.
